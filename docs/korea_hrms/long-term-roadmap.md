# Korea HRMS 장기 개발 로드맵 (2026 H2 → 1만 사업장)

작성: 2026-07-06. 전제: S1 완료 + QA/QC 47/47 PASS + 실데이터 수락(5월 급여 32/32·신고서 E2E) 상태에서 출발.
아키텍처 불변식 5개(scale-architecture.md §1)를 유지하는 한, 각 단계는 코드 재작성이 아니라 누적이다.

## Phase 1 — 노호 상용 안착 (7월 상반)
**목표: 첫 유료 고객이 실제 월급여 사이클을 이 시스템으로 완료**
- [ ] D-day 개통: DNS `*`·구글/카카오 키·스토리지 키 투입 (LAUNCH_DAY_RUNBOOK, 사용자)
- [ ] 이메일 발송: Email Account(SMTP) 연결 → 명세서 자동 발송 + 메일 AI 채널 활성화 (내부 주소로 발송 리허설 후)
- [ ] 주민번호 커스텀 필드(암호화) 추가 + 노호 주민번호 입력 → 신고서 3종 완전체
- [ ] 6월 급여를 시스템에서 처리 (임포터 → 검증 → 명세서 발송) — 5월은 재현 검증 완료
- [ ] 시급제(파트타임)·일용직 급여의 **시스템 자동 계산** (현재: 확정값 임포트) — 시급×시간·주휴 로직, 파트타임 7명으로 크로스체크
- [ ] P1b: 급여마감 쓰기 경로(runtime apply) UI — 승인 플로우와 함께

## Phase 2 — 제품 완성도·2호 고객 (7월 하반 ~ 8월)
**목표: 온보딩이 재현 가능한 표준 절차가 됨 (2~5호 테넌트)**
- [ ] 카카오 알림톡 (채널 개설+Solapi 심사 7~14일 — 즉시 신청)
- [ ] 브랜드 확정 (SafeClaw 병용 vs NODE 차용) → P2 디자인 스프린트 (토큰 소비·a11y 이월분)
- [ ] 각주 기능 화면 승격 1차: 연말정산·근로계약(테스트 완비 코어) 중 수요 우선
- [ ] AI v2: `call_llm_with_context` 구현 (LLM 키) — 채널·바인딩·쿼터 구조 재사용, 자연대화 승격
- [ ] 온보딩 패키지화: 임포터+공휴일+소셜로그인+AI 토큰+가이드 생성을 원커맨드로
- [ ] 슬랙·디스코드 앱 등록 → 4채널 전면 가동

## Phase 3 — S2 확장 인프라 (9월 ~ 10월)
**목표: 셀프서브 가입 공개, 운영을 사람이 병목이 아니게**
- [ ] 중앙 인증 브로커 auth.safeclaw.kr (구글 리디렉션 URI 1개화 — 테넌트 무한 확장)
- [ ] HR 전용 VM 분리 (모니터링·타 서비스와 격리, 4~8 vCPU)
- [ ] 테넌트 레지스트리 DB화 + 셀프서브 가입 공개 (현재 파이프라인은 실증 완료 상태)
- [ ] 과금: 미터링→요금제 실결제 연결 (PG), 플랜별 쿼터 실운영
- [ ] 오프사이트 백업 이중화 + 복구 RTO 목표 문서화
- [ ] 근로내용확인신고 월 자동 준비 크론 (대상 집계→담당자 확인 요청 알림)

## Phase 4 — 스케일·시즌 대응 (11월 ~ 12월)
**목표: 1만 사업장 수용 구조 실전화 + 연말 시즌**
- [ ] bench 호스트 샤딩 실행 (호스트당 50~100 사이트, frappe_url 라우팅은 구현 완료 — VM 추가만)
- [ ] AI 워커 오토스케일(큐 길이 기반) + SLA 대시보드 공개
- [ ] 연말정산 시즌 기능 전면화 (코어 테스트 71건 보유) — 12월 수요 정점
- [ ] 보안 심화: 침투 점검, 개인정보 처리방침·수탁 계약 체계, 감사 로그 보존 정책
- [ ] 노무법인 파트너 모델 검토 (노무사가 자기 고객 테넌트를 관리하는 멀티 어카운트)

## 상시 원칙
- 모든 급여 숫자는 확정 대장(엑셀 권위)과 1원 단위 크로스체크 후 keep (results.tsv 저널 유지)
- AI는 조회·계산·알림까지 — 확정 행위(마감·신고 제출)는 항상 사람 승인 게이트
- public repo에 고객 데이터·시크릿 절대 금지, 테넌트 격리 불변식 유지
- 신규 기능은 framework-free 코어 + 얇은 래퍼 + 직접실행 테스트 컨벤션

## 보안 잔여 조치 (2026-07-05 리뷰 후속, Phase 1에서 처리)
- 셀프서브 가입(`/signup`)은 **비활성 유지** — 재활성화 전 조건: create_tenant.sh 전 변수 env화 검증(C1 완료), admin 임시비번/DB비번 로그 노출(H1) 제거, 큐 소비-append 경합(L2) 해결, /signup rate limit
- H1: 프로비저닝 로그의 admin 임시비번·MariaDB root 비번 평문 → 로그 미출력 또는 즉시 파기(현재 수동 파기), bench new-site 비번은 argv→env(MYSQL_PWD)로
- M3: get_tenant_records의 filters를 화이트리스트 필드로 제한(현재 반환 필드만 화이트리스트, 필터는 통과 — 같은 테넌트 내 boolean oracle)
- M4: 채널 핸들러의 동기 I/O를 스레드 오프로드(이벤트 루프 블로킹 완화)
