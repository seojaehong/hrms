# 전자계약(전자서명) API 도입 검토 — Korea HRMS 근로계약서 연동

작성일: 2026-07-11
범위: HRMS `employment_contract_doc.py` (근로계약서 초안 빌더/렌더러)가 생성한
계약서를 실제 서명·법적 효력 있는 전자계약으로 전환하기 위한 국내 전자서명 API
후보 검토. 조사는 각 서비스의 공식 웹사이트/개발자 문서(WebSearch·WebFetch)
기준이며, 원문에서 확인하지 못한 항목은 추측하지 않고 **"미확인"**으로 표기한다.

## 1. 법적 배경 (일반, 서비스 무관)

전자서명법(2020년 전부개정) 제3조는 전자서명이 서명·서명날인·기명날인과
동일한 법적 효력을 가진다고 규정하며, 과거 공인인증서에 부여되던 특별한
법적 지위는 폐지되었다. 즉 특정 인증기관 인증서 없이도 당사자 간 서명
의사와 서명 귀속을 증명할 수 있는 방식이면 원칙적으로 유효하다. 다만
개별 서비스가 실제로 어떤 수준의 증거(감사추적·IP·타임스탬프·문서
위변조 방지)를 제공하는지는 서비스마다 다르므로, 아래 표의 "전자서명법
효력" 칸은 **일반 법리(위)를 전제로 한 서비스별 부가 증빙 수준**을 의미한다.
개별 서비스가 자사 페이지에서 전자서명법 적합성을 명시적으로 언급하는지
여부는 확인 항목별로 별도 표기했다.

## 3. 권고

**1순위: 모두싸인(Modusign)** — 이유:
1. API 문서 구조(인증/엔드포인트/에러코드/Webhook)가 4개 서비스 중 가장
   체계적으로 공개되어 있어 통합 난이도를 가장 낮게 추정할 수 있음(개발자
   문서 사이트 `developers.modusign.co.kr`에서 API 소개·에러·Webhook·임베디드
   열람 등 개별 문서 확인).
2. 그룹웨어/ERP 연동 및 근로계약·연봉계약 자동화 활용 사례가 확인되어,
   HRMS 같은 사내 시스템과의 연동 선례가 있음.
3. 국내 시장 점유율이 높아(공공용 API도 별도 존재) 장기적 서비스 안정성
   리스크가 상대적으로 낮음.

다만 API 자체의 추가 과금 여부, 전자서명법 적합성 명시 문구는 **미확인**
상태이므로, 실제 도입 전 계약 담당자(도입 문의 채널)를 통해 다음을 반드시
재확인해야 한다:
- API 연동에 대한 별도 이용료 유무(서명요청 건수 요금제 외 추가 과금 여부)
- 근로계약서 전용 템플릿/필드 매핑 API(§17 필수기재 항목을 템플릿 필드로
  자동 매핑할 수 있는지)
- 감사추적 로그(서명자 IP·타임스탬프·본인확인 수단)의 세부 스펙과 소송
  증거로서의 활용 가능성

차순위 후보로 **도뉴(Donue)**를 보류 검토 대상으로 남긴다 — 근로계약서를
명시적으로 지원 문서에서 언급한 유일한 서비스이나, API 인증 방식·과금
체계가 미확인이라 1순위로 채택하지 않았다.

## 4. HRMS 통합 스케치 (모두싸인 기준, 개념 설계 — 미검증)

```
[HRMS employment_contract_doc.build_employment_contract(data)]
        │  (missing[] 없음 확인 = 사람이 검수 완료)
        ▼
[render_contract_markdown(contract)] → 사람 검토용 마크다운/PDF 변환
        │  (human_approved=True 게이트 통과 후)
        ▼
[전자서명 API 어댑터] (신규 모듈, 예: employment_contract_esignature_api.py)
        │  1) 계약서 PDF/HTML 업로드 또는 템플릿 필드 매핑
        │  2) 서명자(사업주 대표, 근로자) 정보 등록 → API Key 인증 요청
        │  3) 서명 요청 발송 (모바일/웹 링크)
        ▼
[Webhook 수신] → 서명 완료/거부 이벤트 → HRMS 상태 갱신(완료본 저장)
```

- 이 스케치는 개념적 흐름이며, `hrms/regional/south_korea/` 내 실제
  어댑터 모듈 구현은 별도 태스크로 분리한다(본 문서는 API 검토 산출물).
- mutation 경계 원칙 준수: 서명 발송·완료 반영은 `requires_human_approval`
  게이트 통과 후에만 수행하는 별도 API 레이어에서 처리해야 한다(기존
  `employment_contract.py`의 `mutation_boundary` 컨벤션과 동일).

## 5. 조사 방법 및 한계

- WebSearch + WebFetch로 공식 웹사이트/개발자 문서를 조회했다. 로그인이
  필요한 개발자 콘솔, Postman documenter의 JS 렌더링 콘텐츠 등은 페치에
  실패했다(글로싸인 Postman 문서, 유캔싸인 개발자센터 임베딩 페이지 등).
- 요금·API 상세 스펙은 시점에 따라 변동될 수 있으므로, 실제 계약 체결 전
  반드시 각 사 영업/기술 담당자를 통해 최신 조건을 재확인해야 한다.
- 이 문서에 "미확인"으로 표기된 항목은 추측이나 창작 없이 원문 미확보를
  그대로 나타낸 것이다.
