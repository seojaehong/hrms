# Korea HRMS 확장 아키텍처 — 2-플레인 설계 (1→10,000 사용자)

작성: 2026-07-05. 사용자 요구: 최종 릴리즈 = 기존 버전 + AI 버전이며, AI는 "계정 하나 붙이는 것"이 아니라 사용자 1→10→100→1,000→10,000으로 늘어도 재설계 없이 확장 가능해야 한다.

## 0. 현 구조의 정직한 진단 (2026-07-05 실사)

| 항목 | 현재 | 판정 |
|---|---|---|
| 웹 서빙 | `bench serve` (Frappe **개발 서버**, 단일 프로세스) | 릴리즈 불가 — 동시 사용자 수십 명에서 붕괴 |
| 백그라운드 워커/스케줄러 | Procfile에서 제거됨 (redis/watch 라인 삭제된 dev 구성) | 알림·정기작업 미가동 |
| 호스트 | 2 vCPU / 11GB, 모니터링 7컨테이너 + 워드프레스 + n8n과 공유 | 테넌트 ~10개가 물리 한계 |
| 테넌트 모델 | Frappe multi-site (사이트=테넌트, DB 격리) | **유지 가치 높음** — 프라이버시·급여 데이터 격리에 최적, Frappe Cloud가 수천 사이트까지 검증한 패턴 |
| 프로비저닝 | create_tenant.sh (자동화 완성) but DNS 존 권한 없음, 레지스트리가 public repo 파일 | 반자동 — 사람 개입 2곳 |
| AI | stdio MCP(로컬 1인용) | 확장 설계 이전 단계 |

핵심 결론: **테넌트 격리 모델(사이트=테넌트)은 옳으니 유지하고, 서빙과 AI를 분리된 플레인으로 재구성한다.** 재작성(탈 Frappe)은 기각 — Korea 코어 1,061 테스트와 DocType 자산을 버리는 수개월 공사이며, Frappe multi-site는 우리가 가려는 규모까지 이미 검증돼 있다.

## 1. 2-플레인 설계

```
[사용자/직원]                    [사장·실무자 + AI 채널: 텔레그램·슬랙·디스코드·메일·(카카오)]
     │                                        │
     ▼                                        ▼
┌─────────────────────┐          ┌──────────────────────────────┐
│ Plane 1: 레코드 시스템 │          │ Plane 2: AI 플레인 (stateless) │
│ (Frappe multi-site)  │◄─────────│                              │
│                      │ site-scoped│  ① MCP HTTP 게이트웨이        │
│ · 사이트=테넌트(DB격리)│  토큰+REST │  ② AI 워커 (큐 소비, LLM 호출) │
│ · PWA + Desk         │          │  ③ 채널 커넥터 4종(멀티테넌트 봇)│
│ · gunicorn+workers   │          │  ④ 순수 계산 코어(연차·퇴직금 등)│
│ · 스케줄러(브리핑 트리거)│          │     — 이미 stdio MCP로 실물화   │
└─────────────────────┘          └──────────────────────────────┘
        ▲                                     ▲
        └────────── 중앙 테넌트 레지스트리 ──────┘
                (테넌트→bench호스트→도메인→플랜→AI토큰)
```

### 확장 불변식 (이것만 지키면 규모가 바뀌어도 구조가 안 바뀐다)
1. **AI 플레인은 무상태(stateless)** — 대화·설정·데이터는 전부 Plane 1(각 테넌트 DB)과 큐에. AI 워커는 몇 개를 띄우든 동일하게 동작 → 사용자 수 = 워커 수·큐 처리량 문제로 환원.
2. **테넌트 격리는 토큰이 강제** — AI의 모든 데이터 접근은 site-scoped 토큰(sha256 저장) + 해당 사이트 REST로만. 크로스 테넌트 누출이 구조적으로 불가능 (SafeClaw에서 실증한 패턴).
3. **채널 봇은 계정 1개가 멀티테넌트** — 텔레그램/슬랙/디스코드/메일 각각 봇·앱 1개, `채널 사용자 ID ↔ (테넌트, 직원, 권한)` 바인딩 테이블로 라우팅. 테넌트 1만이어도 봇은 여전히 4개.
4. **프로비저닝은 API 1콜** — 가입 → create_tenant(이미 자동화) + AI 토큰 발급 + 채널 초대링크 생성까지 무인. DNS는 와일드카드 1레코드(`*.safeclaw.kr`)로 개입 제로화.
5. **레지스트리는 중앙 DB** — repo 파일(multi_site.json)에서 승격. AI 플레인이 테넌트→bench 호스트 라우팅에 사용 → bench 호스트를 수평으로 늘려도(샤딩) AI 플레인 무수정.

## 2. 규모 단계별 실행 (같은 구조, 배치만 바뀜)

| 단계 | 규모 | Plane 1 | Plane 2 | 해야 할 일 |
|---|---|---|---|---|
| **S1 (지금~NOHO+α)** | 테넌트 1~10 | 현 박스, **gunicorn+workers+scheduler 전환**(즉시) | 같은 박스에 systemd 서비스 2개(MCP 게이트웨이·AI 워커) + 채널 커넥터 | 서빙 전환, AI 플레인 v0, 와일드카드 DNS |
| **S2** | 테넌트 10~100 | **HR 전용 VM 분리**(4~8 vCPU), 모니터링/기타와 격리. DB 튜닝·오프사이트 백업 | 별도 소형 VM 또는 Fly Machines. 레지스트리 DB화 | 셀프서브 가입 플로우, 사용량 미터링(plan별) |
| **S3** | 사용자 ~10,000 (테넌트 수백) | **bench 호스트 샤딩**(호스트당 50~100 사이트) + 중앙 프로비저닝이 호스트 배정 | AI 워커 오토스케일(큐 길이 기반), LLM 비용 테넌트별 미터링·요금제 반영 | 라우팅 자동화(ingress API), 과금, SLA 모니터링 |

각 단계 전환은 "배치 이동"이지 "코드 재작성"이 아니다 — 불변식 1~5를 S1부터 지키기 때문.

## 3. 릴리즈 구성 (최종 릴리즈 = 기존 + AI)

- **기존 버전(Plane 1)**: v1 헤드라인 7영역 (launch-master-plan §2) — 테넌트별 사이트로 제공.
- **AI 버전(Plane 2)**: 추가 요금제 레이어. 같은 테넌트 데이터 위에 ① 채팅(도구 호출) ② 상주 브리핑·마감 알림 ③ 계산 도구(연차·퇴직금·공제 — 화면 없는 기능까지 커버). AI는 읽기+계산+알림, 확정 행위는 사람 승인(기존 preview-only 계약과 정합).
- 요금제 축: registry의 plan(starter/professional/enterprise)에 AI 사용량 쿼터를 붙인다 — S1에서는 미터링 로그만 쌓고 과금은 S2부터.

## 4. S1 실행 체크리스트 (지금 박스에서, 순서대로)

1. **서빙 전환**: Procfile `bench serve` → `gunicorn -w 3` + redis-queue 워커(short/long) + scheduler 복원. 검증: 부하 간이 테스트(동시 50 요청) + 스케줄러 tick 로그.
2. **와일드카드 DNS**: 사용자 대시보드에서 `*.safeclaw.kr` CNAME → 터널 (1회). 이후 테넌트 DNS 개입 제로. create_tenant.sh BASE_DOMAIN=`safeclaw.kr`로 변경.
3. **AI 플레인 v0**: `mcp_server/`를 이중 모드로 — stdio(로컬) + **streamable HTTP**(systemd, 토큰 인증). 토큰 저장은 서버 로컬(파일→S2에서 레지스트리 DB). 도구 2계층: 계산 코어(무DB) + 테넌트 데이터(REST 브리지, site-scoped API key).
4. **채널 커넥터 v0**: 텔레그램부터(기존 봇 인프라 재사용) → 슬랙·디스코드·메일. 모두 바인딩 테이블 경유.
5. **레지스트리 이동**: multi_site.json을 repo 추적에서 제외(서버 전용) — public 노출 차단(이미 발생한 문제의 구조적 해결).

## 4-1. 실행 현황 (2026-07-05)

- **S1 완료**: gunicorn+워커+스케줄러+nginx(도메인→사이트 map), bench named volume, 전 사이트 일일 백업, 5분 스모크 크론. 부하 실측: noho ping 100요청/동시20 → 100% 200, 평균 32ms.
- **S2 선행 구현 완료**:
  - 불변식 3 기반: AI 플레인 v0 가동 (site-scoped 토큰, 읽기전용 브리지, NOHO 실데이터 조회 실증)
  - 불변식 4 **셀프서브 가입 파이프라인**: `POST ai.safeclaw.kr/signup` → 큐 → 크론 워커 → create_tenant 무인 실행. 터널에 `*.safeclaw.kr` 와일드카드 ingress 추가로 테넌트별 DNS/ingress 개입 완전 제거(사용자 와일드카드 DNS 1회만 전제)
  - 과금 기반 **사용량 미터링**: 인증 요청별 site/label/path JSONL
  - 불변식 5: 테넌트 레지스트리 repo 추적 제외(서버 전용) + example 템플릿
- **S2 잔여**: 중앙 인증 브로커(구글 앱 필요), 레지스트리 DB화, 미터링→쿼터/과금 연결, HR 전용 VM 분리
- **S3 잔여**: bench 샤딩, AI 워커 오토스케일, SLA 모니터링

## 5. 기각한 대안 (기록)

- **탈 Frappe 재작성**(FastAPI+Supabase 등): 코어 자산·DocType·권한체계 폐기, 수개월. 일정·리스크 대비 이득 없음.
- **단일 사이트 row-level 멀티테넌시**: Frappe 설계와 충돌, 급여·주민번호 데이터의 테넌트 격리 약화. 기각.
- **처음부터 K8s**: 현 규모에서 운영 복잡도만 증가. S3에서 샤딩으로 충분.
